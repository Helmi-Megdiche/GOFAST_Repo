# #14 PR 4: deploy job Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (no subagents on this PR). Steps use checkbox syntax.

**Goal:** On a green CI run on `main`, build the images once, push them to GHCR tagged with the commit SHA, and deploy that SHA to staging over SSH through a forced command.

**Architecture:** `deploy.yml` (workflow_run of CI) has a `build` job (packages: write) and a `deploy` job in the `staging` environment that does nothing, and says so, while the environment secrets are missing. On the server the `deploy` user can run one thing: `/opt/gofast/deploy.sh`, forced by `authorized_keys`. It validates `SSH_ORIGINAL_COMMAND` before any action, then pulls, runs compose, checks health through Caddy, and rolls back on failure.

**Tech Stack:** GitHub Actions, bash, Docker Compose v2, GHCR. Tests in bash with fake `docker`, `curl`, `git` on `PATH`.

**Spec:** supervisor task comment on #14 (20:47 UTC, 19 Nov 2026). REVIEW.md: RV-12 (twins), RV-22 (refuse before acting), RV-24 (cleanup only what belongs to the target), RV-09 (real counts), RV-11 (docs).

## Global Constraints

- The repo is public: no real host, IP, domain, key or token in any file, test or log line.
- Every third-party action pinned by commit SHA. Prefer none: use plain `docker` in `run` steps.
- Image tag = full 40-hex commit SHA. Images: `api` (api, ws, worker, migrate) and `web`.
- `permissions: contents: read` at top; `packages: write` on the build job only.
- No `set -x` anywhere near secrets. Secrets only through `env:`, never in a command line or an echo.
- Deploy job skipped (not failed) while `STAGING_HOST`, `STAGING_SSH_KEY`, `STAGING_KNOWN_HOSTS` do not exist; the summary says so.
- Forced command accepts only `deploy <40-hex>` or `rollback`.
- Rollback is code only. Migrations are forward only.

## Review Focus

- A command with a newline, a tab, uppercase hex, 39 or 41 hex chars, or a trailing space: refused, zero docker calls.
- A SHA that is not on `main` (fork commit fetched by hash): refused before any pull.
- The first deploy ever (no `current`): a failed health check has nothing to roll back to; exits non-zero, state untouched.
- Two deploys at once: the second waits or is refused, never interleaves.
- Pull token or basic-auth password in a log line or a process argument list.
