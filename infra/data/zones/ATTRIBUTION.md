# Délégation boundaries: data source

The boundaries of the 48 délégations of the Grand Tunis (Tunis, Ariana, Ben Arous, Manouba; decision D1)
in `delegations.geojson` and migration `0009_zones_grand_tunis.sql` come from OpenStreetMap.

**© OpenStreetMap contributors.** The data is available under the Open Database Licence (ODbL) 1.0:
https://www.openstreetmap.org/copyright

- The extract is one-time (`extract.mjs`, OSM data of the timestamp written in `delegations.geojson`). The
  app never calls OpenStreetMap: it reads the boundaries from its own database (`core.zones`).
- A derived database must stay under ODbL and keep this credit. The public zones page (FE-04, web) shows
  "© OpenStreetMap contributors" with the link above.
- OSM `admin_level` in Tunisia: 4 governorate, 5 délégation (used here), 6 imada (sector, not used).
- `name` is the French OSM name (`name:fr`) without the "Délégation (de)" prefix; `name_ar` is `name:ar`;
  `name_en` is `name:en`, else the French name.

## Load

The boundaries are loaded by migration `apps/api/migrations/0009_zones_grand_tunis.sql`, so every migrated
database (production, tests, a developer's laptop) has the 48 délégations, all active (D1). The migration is
generated by `extract.mjs` from `delegations.geojson`; do not edit it by hand.

## Refresh

`node infra/data/zones/extract.mjs` downloads the data again (network, a few minutes) and rewrites
`delegations.geojson` and the migration. Once 0009 is on `main` it is never edited: a refresh is a NEW
migration (copy the generated file under the next number, as an update of `core.zones` by name).
`node infra/data/zones/extract.mjs --refresh-names` reads only the names again (Overpass) and keeps the committed
boundaries. `node infra/data/zones/extract.mjs --from-geojson` rewrites the migration from the committed GeoJSON without
the network.
